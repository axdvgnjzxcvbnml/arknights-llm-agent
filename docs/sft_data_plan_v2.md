## 二、A 类：结构化推理链

### 2.1 数据来源

- **游戏状态**：从 `env/mock_env.py` 生成多样化的 GameState（不同关卡、不同费用、不同敌人组合）
- **强模型生成**：Qwen3-8B-Thinking（或更强的模型）对每个状态生成推理链
- **私服验证**：用私服（明日方舟私服或模拟器）验证推理链中的关键判断是否正确

### 2.2 生成流程

```
Step 1: 生成多样化 GameState
  ├── 从 PRTS 关卡数据提取关卡配置（敌人波次、地图、部署限制）
  ├── 随机化初始状态（费用 0-30、生命 1-20、已部署干员 0-5）
  ├── 覆盖主要关卡类型（主线 1-12 章、活动关、剿灭）
  └── 输出：10000+ 个多样化 GameState

Step 2: 强模型生成推理链
  ├── 输入：GameState 的自然语言描述（state_to_text.py 生成）
  ├── Prompt：要求模型输出 reasoning（分析过程）+ 至少 2 个候选方案 + 优劣对比
  ├── 模型：Qwen3-8B-Thinking（V100 上运行）
  └── 输出：{reasoning, candidates[], recommendation}

Step 3: 私服验证筛选
  ├── 对推理链中的关键判断（如"这个敌人法抗高"）进行验证
  ├── 验证方式：查 PRTS 数据 / 私服实际测试 / 规则校验
  ├── 筛选标准：推理逻辑自洽 + 关键事实正确 + 候选方案合理
  └── 淘汰率预估：30-50%（强模型生成的推理链质量参差不齐）

Step 4: 格式转换
  ├── question: GameState 自然语言描述
  ├── answer: reasoning + 候选方案 + 推荐 + 优劣分析
  ├── evidence: inferred（模型推理，非事实）
  └── 输出：SFT 训练对
```

### 2.3 验证方式

- **逻辑自洽性检查**：reasoning 中的前提是否支持结论
- **事实正确性检查**：涉及干员/敌人/关卡数值的部分是否与 PRTS 一致
- **候选方案合理性**：至少 2 个方案，且各有优劣（不能全是同一个方案的变体）
- **人工抽查**：随机抽 5% 人工审核

### 2.4 预计工作量

| 阶段 | 工作量 | 说明 |
|------|--------|------|
| GameState 生成 | 1-2 天 | 脚本化，从 PRTS 数据提取 |
| 强模型推理 | 3-5 天 | V100 上运行，10000 条 × ~10s/条 |
| 私服验证 | 2-3 天 | 需要私服环境，半自动 |
| 筛选+格式转换 | 1 天 | 脚本化 |
| **合计** | **7-11 天** | |

### 2.5 预估数据量

- 生成：10000 条
- 筛选后：5000-7000 条（淘汰率 30-50%）

## 三、B 类：证据分级

### 3.1 数据来源

- **PRTS 数值**：干员属性、敌人面板、关卡配置 → evidence: fact
- **攻略文本**：PRTS 攻略、B站攻略 → evidence: retrieved
- **均匀估算**：波次时间轴、敌人出现时间 → evidence: estimated
- **模型推断**：战术判断、推荐理由 → evidence: inferred
- **不知道**：模型不确定时 → evidence: unknown

### 3.2 生成流程

```
Step 1: 构建查询模板
  ├── 干员类："XX干员的攻击/防御/费用是多少？"
  ├── 敌人类："XX敌人的生命值/法抗/攻击力是多少？"
  ├── 关卡类："XX关卡的敌人配置/部署限制是什么？"
  ├── 技能类："XX干员的XX技能效果/冷却/初始技力是多少？"
  ├── 攻略类："XX关卡怎么打？"（从攻略文本检索）
  ├── 估算类："XX关卡第X波敌人什么时候出现？"（均匀估算）
  └── 不确定类："XX干员的隐藏属性是什么？"（PRTS 没有的数据）

Step 2: 自动生成问答对
  ├── 从 PRTS JSON 提取数值 → 生成 fact 类问答对
  ├── 从攻略文本检索 → 生成 retrieved 类问答对（标注来源）
  ├── 从波次时间轴估算 → 生成 estimated 类问答对（标注估算方法）
  ├── 构造不确定查询 → 生成 unknown 类问答对（答案必须说"不知道"）
  └── 每条问答对必须标注 evidence 级别和来源

Step 3: 质量校验
  ├── fact 类：数值与 PRTS JSON 完全一致
  ├── retrieved 类：来源 URL 可访问，内容与攻略一致
  ├── estimated 类：标注估算方法（均匀估算/线性插值）
  ├── unknown 类：答案明确说"不知道"，不编造
  └── evidence 标注准确率检查（随机抽 10% 人工验证）
```

### 3.3 验证方式

- **数值准确性**：fact 类问答对的数值必须与 PRTS JSON 完全一致（自动校验）
- **evidence 标注准确率**：随机抽 10% 人工验证 evidence 级别是否正确
- **"不知道"覆盖率**：不确定类查询必须说"不知道"，不能编造（自动检查关键词）
- **来源可追溯**：retrieved 类必须有来源 URL

### 3.4 预计工作量

| 阶段 | 工作量 | 说明 |
|------|--------|------|
| 查询模板设计 | 1 天 | 覆盖干员/敌人/关卡/技能/攻略/估算/不确定 |
| 自动生成脚本 | 2-3 天 | 从 PRTS JSON + 攻略文本批量生成 |
| 质量校验 | 1-2 天 | 自动校验 + 人工抽查 |
| **合计** | **4-6 天** | |

### 3.5 预估数据量

- 干员类：460 干员 × 5 属性 = 2300 条
- 敌人类：500 敌人 × 4 属性 = 2000 条
- 关卡类：487 关卡 × 3 属性 = 1461 条
- 技能类：460 干员 × 3 技能 = 1380 条
- 攻略类：100 关卡 × 2 攻略 = 200 条
- 估算类：100 关卡 × 3 波次 = 300 条
- 不确定类：200 条
- **合计：约 7841 条**，筛选后 3000-5000 条

## 四、C 类：工具调用

### 4.1 数据来源

- **Agent 运行日志**：从 `decision_loop.py` 和 `env/arknights_env.py` 的运行日志中抽取
- **成功轨迹**：调用了工具且结果被正确使用、最终决策合理的轨迹
- **工具列表**：query_operator, query_skill, query_enemy, query_stage, search_guide, recommend_operators

### 4.2 生成流程

```
Step 1: 积累 Agent 运行日志
  ├── 跑通 Agent 闭环（mock 环境 + mock LLM）
  ├── 记录每步的：输入状态、调用的工具、工具参数、工具返回、最终决策
  ├── 跑 100+ 局完整对局，积累 1000+ 步决策日志
  └── 日志格式：JSONL，每步一条

Step 2: 抽取成功轨迹
  ├── 筛选标准：
  │   ├── 调用了至少 1 个工具
  │   ├── 工具返回结果被决策使用（不是调了不用）
  │   ├── 最终决策合理（动作合法、费用足够、干员可用）
  │   └── 工具调用参数正确（干员名/关卡ID存在）
  ├── 淘汰：工具调用错误、参数错误、调了不用的轨迹
  └── 输出：成功工具调用轨迹

Step 3: 格式转换
  ├── question: GameState 自然语言描述 + "你会怎么做？"
  ├── answer: 工具调用序列（工具名+参数+理由）→ 综合决策
  ├── evidence: inferred（工具调用是推理过程）
  ├── 必须包含：为什么调用这个工具、工具返回了什么、如何使用返回结果
  └── 输出：SFT 训练对

Step 4: 多样化增强
  ├── 同一状态生成不同的工具调用序列（查不同的工具）
  ├── 构造需要多工具协作的场景（先查关卡敌情→再查推荐干员→再查干员技能）
  └── 增加工具调用的多样性
```

### 4.3 验证方式

- **工具调用正确性**：工具名存在、参数格式正确、参数值合法（自动校验）
- **结果使用率**：工具返回结果必须在 answer 中被引用（自动检查）
- **决策合理性**：最终决策的动作必须合法（自动校验）
- **人工抽查**：随机抽 10% 人工审核工具调用理由是否合理

### 4.4 预计工作量

| 阶段 | 工作量 | 说明 |
|------|--------|------|
| Agent 闭环跑通 | 2-3 天 | mock 环境 + mock LLM，积累日志 |
| 成功轨迹抽取 | 1-2 天 | 脚本化筛选 |
| 格式转换+增强 | 1 天 | 脚本化 |
| **合计** | **4-6 天** | |

### 4.5 预估数据量

- 100 局 × 平均 15 步 = 1500 步决策日志
- 成功轨迹筛选率：~50%（需要调用工具且使用正确）
- 多样化增强：×1.5
- **合计：约 1125 条**，目标 2000-3000 条（需要跑更多局）

### 4.6 依赖

- **必须先跑通 Agent 闭环**：decision_loop.py + env/arknights_env.py + mock LLM
- **需要积累足够的运行日志**：至少 100 局完整对局
- **V100 上线后可用真实 LLM 跑更多局**：数据质量更高

## 五、D 类：战术常识

### 5.1 数据来源

- **攻略文本**：PRTS 攻略、B站攻略专栏
- **视频文本**：血狼破军等第三方分析视频（video_extract 提取的口播文本）
- **LLM 抽规则**：用 LLM 从攻略/视频文本中抽取战术原则
- **人工审核**：对抽取的规则进行人工审核，确保正确且泛化

### 5.2 生成流程

```
Step 1: 收集攻略/视频文本
  ├── PRTS 攻略文本：从 data/prts_raw/ 的攻略 JSON 提取
  ├── 视频口播文本：从 video_extract 提取的血狼破军视频 ASR 文本
  ├── 覆盖主题：职业克制、费用管理、部署顺序、技能时机、干员定位
  └── 输出：100+ 篇攻略/视频文本

Step 2: LLM 抽取战术规则
  ├── 输入：攻略/视频文本片段
  ├── Prompt：从文本中抽取可泛化的战术原则，只说原则不绑坐标
  ├── 输出格式：{rule: "原则描述", category: "职业克制/费用管理/...", source: "来源"}
  ├── 过滤：排除绑坐标的规则（如"3-8 放在 A3"）、排除过于具体的操作
  └── 输出：候选战术规则列表

Step 3: 人工审核
  ├── 审核标准：
  │   ├── 规则正确（符合游戏机制）
  │   ├── 规则泛化（不绑具体关卡/坐标）
  │   ├── 规则有价值（不是废话，如"干员要部署"）
  │   └── 规则可操作（能指导决策）
  ├── 审核方式：逐条审核，标记通过/修改/淘汰
  ├── 修改：对有小问题的规则进行修改后通过
  └── 淘汰：错误、不泛化、无价值的规则

Step 4: 生成问答对
  ├── question: 场景化提问（如"面对高防御敌人应该用什么类型干员？"）
  ├── answer: 战术原则 + 解释 + 举例（不绑坐标）
  ├── evidence: inferred（战术原则是推理/经验总结）
  ├── 必须包含：原则描述、为什么、适用场景、反例（什么时候不适用）
  └── 输出：SFT 训练对
```

### 5.3 验证方式

- **规则正确性**：人工审核，确保符合游戏机制
- **规则泛化性**：检查是否绑坐标/具体关卡，必须可泛化
- **问答对质量**：answer 必须包含原则+解释+适用场景，不能只给一句话
- **人工抽查**：100% 人工审核（D 类数据量小，必须全审）

### 5.4 预计工作量

| 阶段 | 工作量 | 说明 |
|------|--------|------|
| 收集文本 | 1-2 天 | PRTS 攻略已有，视频文本需 video_extract |
| LLM 抽规则 | 1-2 天 | V100 上运行，批量抽取 |
| 人工审核 | 3-5 天 | 逐条审核，最耗时 |
| 生成问答对 | 1 天 | 脚本化 + 人工润色 |
| **合计** | **6-10 天** | |

### 5.5 预估数据量

- 抽取候选规则：2000-3000 条
- 人工审核通过率：~50%
- 生成问答对：每条规则生成 1-2 个场景化问答
- **合计：1000-2000 条**

### 5.6 关键约束

- **只说原则，绝不绑坐标**：D 类数据的核心约束，违反的规则必须淘汰
- **100% 人工审核**：D 类数据量小但质量要求高，必须全审
- **血狼破军视频是重要来源**：video_extract 提取的口播文本包含大量战术分析

## 七、私服验证接口需求

### 7.1 为什么需要私服验证

A 类数据（结构化推理链）的质量取决于推理链中的关键判断是否正确。强模型生成的推理链可能包含错误的事实判断（如"这个敌人法抗高"但实际法抗为 0）。需要私服验证来筛选掉包含错误事实的推理链。

### 7.2 私服验证接口设计

```python
# 验证接口（部署在私服或模拟器上）
class PrivateServerValidator:
    """私服验证器：验证推理链中的关键判断是否正确"""

    def validate_enemy_stat(self, enemy_name: str, stat: str, value: float) -> bool:
        """验证敌人属性是否正确
        例：validate_enemy_stat("碎骨", "defense", 200) → True/False
        """

    def validate_operator_stat(self, operator_name: str, stat: str, value: float) -> bool:
        """验证干员属性是否正确"""

    def validate_skill_effect(self, operator: str, skill: str, effect_desc: str) -> bool:
        """验证技能效果描述是否正确"""

    def validate_stage_config(self, stage_id: str, config: dict) -> bool:
        """验证关卡配置（敌人波次/部署限制）是否正确"""

    def validate_deployment(self, stage_id: str, operator: str, grid: str, direction: str) -> bool:
        """验证部署是否合法（格子可部署/干员未部署/费用足够）"""

    def simulate_battle(self, stage_id: str, actions: list) -> dict:
        """模拟战斗，验证动作序列是否能通关
        返回：{win: bool, life_remaining: int, reason: str}
        """
```

### 7.3 私服验证的替代方案

如果私服不可用，可以用以下替代方案：

| 方案 | 说明 | 准确率 |
|------|------|--------|
| PRTS 数据校验 | 从 PRTS JSON 验证数值类判断 | ~95%（数值准确） |
| 规则引擎校验 | 用游戏机制规则验证逻辑类判断 | ~80%（规则覆盖有限） |
| 强模型自洽性检查 | 用另一个强模型验证推理链是否自洽 | ~70%（可能互相认同错误） |
| 人工审核 | 人工验证关键判断 | ~99%（但慢且贵） |

**建议：** 首批 500 条用 PRTS 数据校验 + 人工抽查，后续大规模生成时再接私服验证。

### 7.4 私服验证的接口需求总结

- **必须接口**：validate_enemy_stat, validate_operator_stat, validate_skill_effect, validate_stage_config
- **重要接口**：validate_deployment（验证部署合法性）
- **理想接口**：simulate_battle（模拟战斗验证动作序列）
- **部署方式**：HTTP API 或本地 Python 库，供数据生成脚本调用
- **优先级**：首批 500 条不需要私服，用 PRTS 数据校验替代；大规模生成（5000+ 条）时需要私服

## 八、统一 SFT 格式

### 8.1 数据格式

```json
{
  "id": "unique-id",
  "category": "A|B|C|D",
  "question": "自然语言问题/状态描述",
  "answer": "自然语言回答（含 reasoning + 决策 + 理由）",
  "evidence": "fact|retrieved|inferred|estimated|unknown",
  "source": {
    "type": "prts|guide|video|agent_log|model_generated",
    "url": "来源URL（如有）",
    "stage_id": "相关关卡（如有）"
  },
  "metadata": {
    "generated_at": "2026-09-30",
    "validator": "prts_check|human|private_server",
    "quality_score": 0.9
  }
}
```

### 8.2 各类数据的 evidence 标注

| 类别 | evidence | 说明 |
|------|----------|------|
| A. 推理链 | inferred | 模型推理，非事实 |
| B. 证据分级 | fact/retrieved/estimated/unknown | 根据查询类型标注 |
| C. 工具调用 | inferred | 工具调用是推理过程 |
| D. 战术常识 | inferred | 战术原则是经验总结 |

### 8.3 train/eval 切分

- **按关卡维度切分**：避免同一关卡的数据同时出现在 train 和 eval（数据泄漏）
- **比例**：9:1（train 90%，eval 10%）
- **输出**：`sft_train.jsonl`、`sft_eval.jsonl`
- **与 configs/training.yaml 对齐**

- [ ] 生成多样化 GameState

- [ ] 跑通 Agent 闭环，积累运行日志

- [ ] 输出：2000-3000 条 C 类数据

### Phase 5：合并与训练（2-3 天）
- [ ] 合并四类数据

- [ ] V100 上训练 SFT

## 十、风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| 强模型生成的推理链质量差 | A 类数据淘汰率高，数据量不足 | 降低首批目标（500 条），验证质量后再扩大 |
| 私服不可用 | A 类数据验证困难 | 用 PRTS 数据校验 + 人工抽查替代 |
| 人工审核工作量大 | D 类数据进度慢 | 降低 D 类首批目标（100 条），优先审核高价值规则 |
| Agent 闭环未跑通 | C 类数据无法生成 | C 类排最后，先做 B/D/A 类 |
| 数据质量参差不齐 | 训练效果差 | 每类数据都有质量校验环节，不合格的淘汰 |
| 四类数据格式不统一 | 训练时需要额外处理 | 统一 SFT 格式（见第八节），生成时即统一 |
